# 05 — Decide CW decoding by radio mode, not by segment mode

Status: resolved

A WAV segment that started in another mode should still be CW-decoded if the
radio was switched to CW *during* it. Today the decision is made from the
segment's own recorded mode, so those are missed.

The machinery is largely present: `decode_long_segment`/`cw_subranges` already
find telemetry-confirmed CW sub-ranges inside a long segment. This is about
rebasing the *decision* on radio mode from telemetry rather than on the
segment's metadata.

Depends on `--telemetry`; without it there is nothing to rebase on.

## Agent Brief

**Category:** bug
**Summary:** The CW trust decision reads the Logged mode at a segment's *start*
instead of across its span, so CW received after a mid-segment mode change is
decoded and then silently thrown away — and CW that stopped mid-segment is
trusted for the whole of it.

**Current behavior:**

Three pieces, and the gap is between them:

- `decode_segment` is mode-blind. Every segment shorter than `MAX_OVER_S` is
  decoded whole, whatever mode it was in, and `gate_events` judges the result
  on SNR/quality/dominance alone.
- `cw_subranges`/`decode_long_segment` do consult telemetry-confirmed mode, but
  are reachable only from the `dur > MAX_OVER_S` branch.
- `ticker_chunks` decides whether a short segment's decoded events are shown by
  asking `build_state_events` for the mode at the segment's *start* only, and
  keeping or dropping the whole segment on that one answer. `SegState` already
  carries the mid-segment subdivision this needs; it is sampled once and the
  rest discarded.

So a ≤35 s listening segment that started in SSB or FM and was switched to CW
partway decodes correctly and is then dropped. The mirror case — started in CW,
switched away — passes the non-CW remainder's decode through untouched.

Measured on the 2026-jul round (707 segments, 679 of them short, derived UTC
offset 0): 51 short segments contain a telemetry-visible mode change. Nine
start non-CW and contain a CW span; three of those carry real text that is
dropped today:

```
20260706_164711A  FM   'HA5 SHA5R EA DEHA1VHF '
20260706_165056A  SSB  'TEST HA5MIG TEST HA5MIG '
20260706_170237A  SSB  'HA5LADE 5E HA5OO BK '
```

Eight start in CW and change; one of them, `20260706_170747A` (CW until 13.0 s
of 31.7 s), currently reaches the ticker as
`'SGT5 S ME IEEEERR EM O H E C EN IT NIDNAA E TU E TNDV A TEI'`.

**Desired behavior:**

A short segment's CW is decoded and trusted per telemetry-confirmed CW span,
the same way a too-long one already is — the segment's own starting mode stops
being the deciding input.

Two details the sub-range path needs before it can carry short segments:

- **Adjacent CW spans merge before decoding.** `SegState` runs subdivide on
  frequency as well as mode, so one continuous CW period comes back as several
  touching ranges (a real case: `(3,4) (4,5) (5,7) (7,27.1)`). Decoded
  separately, a one-second sliver has no chance — `_estimate_dit` needs several
  ON runs to estimate from. Spans that touch are one span. This is a latent
  defect on the existing long-segment path too, and fixing it there is the same
  fix.
- **A segment with no state coverage keeps today's behavior.** `build_state_events`
  skips a segment whose WAV carries no IC-9700 metadata, so it has no spans to
  decode; it must still be decoded whole and trusted, which is what
  `ticker_chunks`' current "unknown mode passes" branch does. Zero such segments
  exist across the three real rounds in the tree, so this is the non-IC-9700
  path and nothing else.

Excluding the non-CW head is a quality improvement, not just a filter: for
`20260706_170237A` the whole-segment decode is `'E E HA5LADE 5E HA5OO BK '`,
where the leading `'E E '` is the SSB audio before the switch.

**Key interfaces:**

- `cw_subranges(seg, state_events)` — returns segment-relative `(t0, t1)`
  spans. Should return merged spans. Its docstring's "only meaningful for a
  segment too long to decode as a whole" no longer holds and needs rewriting.
- `decode_long_segment(seg, state_events, pitch)` — named for the case it was
  built for; if it becomes the path for every segment, the name is now wrong
  (`Segment` and CONTEXT.md's **Over** are the vocabulary to name it from).
  Its `check_duration=False` reasoning still applies unchanged.
- `ticker_chunks(segs, state_events, long_cw_spans)` — the mode decision lives
  here today and should not: once spans are decoded per-mode, this stops
  filtering by mode and just concatenates. Its docstring explains the current
  filter and must be rewritten, not left describing a gate that has moved.
- `Segment.events` — its only consumers are `ticker_chunks` and
  `contest_video`'s "N characters from M trusted overs" counters. `qso_windows`
  deliberately does not read it (see `burst_starts`) and must stay that way.
  Whether short-segment output keeps living on `Segment.events` or moves into
  the same span list as the long-segment output is the implementer's call;
  both counters must stay correct either way.
- `--skip-gaps` — `remap_audio_t` takes a `long_cw_segs` set of `id(seg)` to
  protect segments whose only content is a recovered CW span. If short segments
  start producing spans, check whether that set's membership rule still says
  what it means.

**Acceptance criteria:**

- [ ] A short segment whose telemetry shows a mid-segment switch *into* CW
      yields trusted CW text for the CW span, and none from the rest.
- [ ] A short segment whose telemetry shows a switch *out of* CW yields text
      from the CW head only.
- [ ] Touching CW spans within one segment are decoded as a single span, for
      both short and too-long segments.
- [ ] A segment with no WAV metadata at all is still decoded whole and trusted
      exactly as today.
- [ ] Behavior without `--telemetry` is unchanged: state runs then come from
      WAV metadata alone, one per segment, so every span is the full segment.
- [ ] Against `2026-jul/`, the three segments listed above produce exactly the
      text quoted, and `20260706_170747A` produces none. (Checked: the quoted
      strings are identical whether the spans are merged or fragmented, so they
      do not encode an accidental property of the current sub-division.)
- [ ] Against `2026-jul/`, the count of CW-start short segments producing
      trusted text stays at 133 of 679, with `20260706_170747A` the only
      change.
- [ ] Tests are written red-first against the unfixed code; the whole suite
      passes; `uv run ruff check .` is clean over the project.

**Out of scope:**

- `MAX_OVER_S` and the other three trust gates keep their values. This ticket
  changes *which audio* is offered to the gate, not how the gate judges.
- The known dit-estimation limitation when two stations key at different
  speeds within one span (documented on `decode_long_segment`).
- The `FREQ_MATCH_TOLERANCE_HZ` subdivision behavior — spans merging for the
  purpose of decoding does not mean frequency should stop subdividing
  `state_events`, which the HUD reads for its own reasons.
- Anything about how the ticker renders. This is upstream of the display.

## Resolution

> *This was generated by AI during triage.*

Done in `dacdce4`, `6588939`, `63e5b33`, `cc0a98c`.

The defect was where the brief said: the decode was mode-blind and
`ticker_chunks` dropped the result, sampling the state runs once at the
segment's start. `decode_round` now decodes the CW-mode spans telemetry
confirms for every segment, not only those past `MAX_OVER_S`, and
`ticker_chunks` filters nothing.

Every acceptance criterion holds, measured against `2026-jul/`: ticker 2099 ->
2072 characters, the three quoted exchanges arrive with exactly the text
predicted, `20260706_170747A`'s 59 characters of trusted noise stop arriving,
and it is the only one of the 133 CW-start short segments to change. Checked
against `2026-aug/` too: 1704 -> 1716 characters, nothing lost.

One thing the brief did not anticipate. Joining touching spans is not a pure
win: on `20260706_171916A`, an 86 s segment, the joined decode loses
`'AND HAH TEST'` that one of the fragments had produced. That is the known
cost of estimating a single dit length across a span where two stations key at
different speeds, already documented on `decode_cw_subranges`. It was taken as
worth the 'ETE' / 'AE ' / 'EK ' / 'EHBHKHBTEV ' slivers it removes elsewhere,
but it is a judgement call, not a measurement.
